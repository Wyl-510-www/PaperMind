# Phase 3: 元数据管理与标签过滤 - 需求文档

## 概述

**目标**：完善笔记的元数据管理，支持按标签和时间范围过滤检索。

**背景**：Phase 2.2 已实现 PDF 笔记上传和基础文本提取，但缺少元数据管理和结构化检索能力。用户无法按主题标签或时间范围快速定位笔记，检索效率低。

**价值**：通过标签分类和时间过滤，用户可以快速缩小检索范围，提升笔记管理效率和查询精准度。

---

## 功能范围

### 3.1 扩展元数据字段

为每条笔记增加以下元数据字段：

| 字段名 | 类型 | 必填 | 说明 | 示例 |
|--------|------|------|------|------|
| `title` | 字符串 | ✅ 是 | 论文标题 | "Attention Is All You Need 阅读笔记" |
| `author` | 字符串 | ❌ 否 | 论文作者 | "Vaswani et al." |
| `year` | 字符串 | ❌ 否 | 发表年份/会议 | "2017" 或 "NeurIPS 2017" |
| `read_date` | 日期 | ✅ 是 | 阅读日期 | "2026-01-13"（自动填充当天，可修改）|
| `tags` | 字符串数组 | ✅ 是 | 标签列表 | ["长期记忆", "Transformer"] |
| `note_type` | 枚举 | ✅ 是 | 笔记类型 | "摘要" / "详细笔记" / "评论" / "问题" |

**设计决策**：
- `title` 和 `note_type` 必填，确保笔记基本分类明确
- `tags` 必须至少选择一个标签（多选）
- `author` 和 `year` 选填，保持输入流程简洁
- `read_date` 默认填充当天日期，用户可修改为实际阅读日期

### 3.2 预定义标签库

**研究领域**：NLP 中的长期记忆管理

**标签列表（10 个核心标签，扁平化结构）**：

1. 长期记忆
2. 记忆架构
3. 知识图谱
4. 向量数据库
5. RAG（检索增强生成）
6. Agent 智能体
7. Transformer
8. 注意力机制
9. 评测基准
10. 应用案例

**设计决策**：
- 扁平化标签，避免层级结构的复杂性
- 标签数量精简到 10 个核心标签，降低用户选择负担，覆盖最关键的研究主题
- 标签名称使用中文，符合目标用户习惯
- 用户无法自定义标签（Phase 3 限制，后续可扩展）

### 3.3 检索策略优化

**两阶段检索流程**：

#### 阶段 1：硬过滤（标签 + 时间范围）

用户可选择：
- **标签过滤**：多选标签，使用 **OR 逻辑**（匹配任一标签即可）
- **时间范围**：
  - 全部时间（默认，不过滤）
  - 本周（过去 7 天）
  - 本月（当前月份）
  - 本年（当前年份）
  - 自定义日期范围（用户输入起止日期）

**过滤逻辑**：
```python
# 伪代码
filtered_memory_ids = query_mysql(
    tenant_id=current_tenant,
    tags__overlap=selected_tags,  # OR 逻辑
    read_date__gte=start_date,
    read_date__lte=end_date
)
```

#### 阶段 2：语义检索（向量相似度）

- 对过滤后的 Memory IDs 进行 embedding 相似度检索
- 调用 Reranker 精排
- 返回 Top-K 最相关笔记

**特殊情况处理**：
- 如果用户未选择标签和时间，直接进行全局语义检索（保持 Phase 2 行为）
- 如果硬过滤后无结果，提示"未找到符合条件的笔记，请尝试调整过滤条件"
- 如果硬过滤有结果但语义检索无匹配（相似度过低），提示"找到 N 条符合标签/时间条件的笔记，但与查询语义相关性较低"

#### 笔记输入页面

**手动输入笔记**：
- 标题输入框（必填）
- 笔记内容文本框（必填）

- 笔记类型下拉菜单（摘要/详细笔记/评论/问题，必选）

**PDF 上传笔记**：
- 保持现有 PDF 上传功能
- 文本提取后自动填充到"笔记内容"
- 用户补充元数据（标题、标签、笔记类型等）

#### 查询页面

**查询表单**：

  - 选项：全部时间 / 本周 / 本月 / 本年 / 自定义
  - 如选择"自定义"，显示日期范围选择器

**结果展示优化**：

  ```
  📝 笔记内容：

  ```
- 标签高亮显示（不同标签用不同颜色徽章）
- 如果使用了标签过滤，匹配的标签加粗或特殊标记

## 数据模型变更

### Memory V2 metadata 字段扩展

现有 Memory 表的 `metadata` 字段（JSON 类型）需包含以下键：

```json
{
  "title": "Attention Is All You Need 阅读笔记",
  "author": "Vaswani et al.",
  "year": "2017",
  "read_date": "2026-01-13",
  "tags": ["长期记忆", "Transformer", "注意力机制"],
  "note_type": "详细笔记"
}
```

**数据库索引优化（可选）**：
- 如果 MySQL 支持 JSON 字段索引，可为 `metadata->tags` 和 `metadata->read_date` 创建索引
- 如查询性能不佳，可在后续 Phase 将 `tags` 和 `read_date` 提升为独立列

## 验收标准

### 功能完整性
- ✅ 手动输入笔记时可填写完整元数据（标题、标签、笔记类型必填）
- ✅ PDF 上传后可补充元数据
- ✅ 查询时可选择标签过滤（多选，OR 逻辑）
- ✅ 查询时可选择时间范围（本周/本月/本年/自定义）
- ✅ 组合过滤生效：先硬过滤（标签+时间）→ 再语义检索
- ✅ 笔记展示包含所有元数据（标题、作者、日期、标签、类型）

### 边界情况
- ✅ 未选择标签和时间时，直接全局语义检索（兼容 Phase 2 行为）
- ✅ 硬过滤无结果时，显示明确提示信息
- ✅ 标签过滤使用 OR 逻辑：选择 2 个标签，返回包含任一标签的笔记
- ✅ 时间范围计算准确：本周/本月/本年基于当前日期动态计算

### 数据一致性
- ✅ 所有新保存的笔记都包含完整元数据
- ✅ 标签值必须在预定义列表中（后端验证）
- ✅ 笔记类型必须为 4 种预定义类型之一
- ✅ 阅读日期格式为 ISO 8601 日期（YYYY-MM-DD）

## 技术约束

### 保持现有技术栈
- Memory V2 核心逻辑不变
- 继续使用 Streamlit 作为 UI 框架
- 继续使用 MySQL metadata JSON 字段存储元数据
- 继续使用 Qdrant 进行向量检索

### 新增依赖
- **无新增第三方库**
- 使用 Python 标准库 `datetime` 处理日期计算
- 使用 Streamlit 内置组件（`st.multiselect`, `st.date_input`, `st.selectbox`）

### 明确不包含
- ❌ 用户自定义标签（Phase 3 不支持，后续可扩展）
- ❌ 标签层级结构（保持扁平化）

- ❌ 笔记删除功能（留给 Phase 6）
- ❌ 标签统计和可视化（后续可扩展）

## 用户场景

### 场景 1：按标签快速定位笔记
**用户目标**：查找所有关于"RAG"和"向量数据库"的笔记

**操作流程**：
1. 进入查询页面
2. 标签过滤器中选择"RAG"和"向量数据库"
3. 输入查询："如何优化 RAG 系统的检索性能？"
4. 点击查询

**预期结果**：
- 系统先过滤出包含"RAG"或"向量数据库"标签的笔记
- 再从这些笔记中进行语义检索
- 返回相关度最高的笔记，展示完整元数据

### 场景 2：查看本月阅读的笔记
**用户目标**：回顾本月阅读了哪些论文

**操作流程**：
1. 进入查询页面
2. 时间范围选择"本月"
3. 输入查询："本月的阅读总结"
4. 点击查询

**预期结果**：
- 系统过滤出 `read_date` 在本月范围内的笔记
- 进行语义检索
- 返回本月阅读的相关笔记

### 场景 3：组合过滤精准检索
**用户目标**：查找上周阅读的关于"Transformer"的论文笔记

**操作流程**：
1. 标签过滤器选择"Transformer"
2. 时间范围选择"本周"
3. 输入查询："Transformer 的注意力机制如何工作？"
4. 点击查询

**预期结果**：
- 先过滤出标签包含"Transformer"且阅读日期在本周的笔记
- 再进行语义检索
- 返回最相关的笔记

## 风险与缓解

### 风险 1：JSON 字段查询性能问题
**描述**：MySQL JSON 字段查询（尤其是数组包含判断）可能性能较差

**缓解措施**：
- Phase 3 先使用 JSON 字段，观察性能
- 如查询慢（>500ms），在后续 Phase 将 `tags` 和 `read_date` 提升为独立列
- 添加适当索引

### 风险 2：时间范围计算边界问题
**描述**：本周/本月/本年的起止时间计算可能存在时区或边界错误

**缓解措施**：
- 使用 Python `datetime` 标准库，避免手写日期计算
- 编写单元测试覆盖边界情况（月初/月末、年初/年末）
- 明确时区使用 UTC 或本地时区（与 Memory V2 保持一致）

### 风险 3：标签列表变更维护成本
**描述**：如果后续需要修改标签列表，需要同步更新代码、UI 和文档

**缓解措施**：
- 将标签列表定义为常量（`constants.py`），避免硬编码
- 提供标签迁移脚本（如需重命名或合并标签）
- 文档中明确标签列表由 `constants.py` 管理
